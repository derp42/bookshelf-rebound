## Ranking and dispositions

- **P0**: exploitable security issue or credible data-loss/data-disclosure risk.
- **P1**: incorrect behavior on a supported, reasonably common path.
- **P2**: compatibility or worthwhile enhancement work.
- **P3**: documentation, usage support, or narrowly scoped behavior.
- **P4**: stale platform, unsupported database/runtime, or deliberately out of scope.
- **FIX**: confirmed defect to implement.
- **ADD**: accepted new capability or documentation/API improvement.
- **VERIFY**: plausible report that needs a current minimal reproduction before a code decision.
- **ALREADY_FIXED**: current Rebound code, dependency floor, or project material already resolves it.
- **DUPLICATE**: covered by another row selected as the canonical action.
- **REJECT**: no Rebound change; rationale and supported alternative are recorded.

## Immediate implementation order

1. **P0: #2122 — resolved** by commits `324d628` and `1780d92`; retain the adversarial object/array, primary-key, explicit-query, and JSON refresh regressions.
2. **P1 correctness cluster** — #2047 and #2091 prevent successful writes from being followed by wrong/failed refreshes; #1939, #1941, #1961, and #2046 repair supported relation paths; #2067 and #2092 replace fragile pagination-count reconstruction.
3. **Small, low-risk fixes** — #2042 and #2114 documentation, then accepted configuration/projection/type work after behavior is specified.

The `VERIFY` rows deliberately do not assert a fix without a current reproduction. The `REJECT` rows are still useful outcomes: they preserve strict relation errors, avoid unsafe/dialect-specific abstractions, and direct users to the supported layer where the behavior belongs.
